# upay Shield

**Fraud, scam, and money-mule intelligence for a modern MFS — built for AI DEV FEST 2026 (DIU-CPC × upay), Track 01: Trust & Risk Intelligence.**

## 1. Project overview

**The problem.** Scam money in mobile financial services usually survives the
first alarm. A victim is tricked (an impersonation call, a fake prize, a
"wrong transfer, please return it" scam) into sending money, and by the time
anyone reports it, the funds have already passed through one or more wallets
and been cashed out at an agent. Investigation today is manual and happens
*after* the damage is done.

**The solution.** upay Shield scores every transaction for risk the instant
it happens, traces where flagged money is moving using a transaction graph
to uncover money-mule pass-through wallets, and gives a human analyst a
plain-language case summary for every alert — so a suspicious transfer can
be **held before the money disappears**, not investigated after.

**Purpose.** Directly targets the challenge's "protect digital money" goal
for Track 01: real-time transaction risk scoring, money-mule and
suspicious-network discovery, and an AI investigation assistant, built on
synthetic data with no production upay data required.

## 2. Features & how AI is used

| Feature | What it does | AI technique |
|---|---|---|
| **Real-time risk scoring** | Scores every transaction 0–100% probability of being suspicious, using behavioral signals (new recipient, amount vs. the sender's own history, new device, transaction velocity, receiver wallet age, fan-in burst to the receiver) | Gradient-boosted decision trees (`scikit-learn GradientBoostingClassifier`) |
| **Mule network discovery** | Builds a transaction graph and flags wallets that collect money from many unrelated senders in a short burst, then cash most of it back out within minutes — the classic money-mule pass-through shape | Graph analytics (`networkx`): fan-in detection, pass-through timing, connected-component clustering |
| **AI investigation assistant** | Turns the structured evidence behind a flagged transaction into a short, plain-English case note an analyst can read in seconds: what happened, why it's risky, what to do next | Rule-based grounded narrative generator, with an optional Claude API mode for a more natural narrative (same evidence, never free-form) |
| **Analyst dashboard** | Lets a human review, hold, approve, or dismiss every flagged transaction — the AI never blocks money on its own | Flask API + a single-page dashboard |

**Why AI, not just rules:** a fixed rule like "block transfers over ৳10,000"
fails for a trader who regularly sends large amounts, and misses a scam
against someone who always sends small amounts. The model instead learns
*relative to each person's own pattern and the destination wallet's
behavior*, which a static threshold can't do — see `evaluation.json` for
measured precision/recall on a held-out test set.

## 3. Technology stack

- **Language:** Python 3.12
- **Data:** pandas, numpy
- **ML:** scikit-learn (GradientBoostingClassifier)
- **Graph analytics:** networkx
- **Backend API:** Flask
- **Frontend:** single-file HTML/CSS/JS dashboard (no build step)
- **Optional GenAI:** Anthropic Claude API (`claude-sonnet-4-6`) for the investigation assistant's natural-language mode
- **Data strategy:** fully synthetic, generated by `data/generate_data.py` — no real upay/customer data is used anywhere (see Section 11 of the hackathon rulebook, "no production data required")

## 4. Requirements

- Python 3.10+
- pip
- ~200 MB disk space (synthetic data + model artifacts)
- No GPU required
- No external API key required to run the full prototype (the Claude API key is optional — see `.env.example`)

## 5. Installation & setup

```bash
# 1. Clone the repo
git clone <your-repo-url>
cd upay-shield

# 2. (Recommended) create a virtual environment
python3 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate

# 3. Install dependencies
pip install -r requirements.txt

# 4. (Optional) configure environment variables
cp .env.example .env
# edit .env if you want to enable the LLM-powered case narrative

# 5. Generate the synthetic dataset
cd data
python3 generate_data.py
cd ..

# 6. Build features, train the risk model, and run mule-network detection
cd backend/app
python3 features.py
python3 train_model.py
python3 graph_analysis.py
python3 generate_demo_snapshot.py   # precomputes the dashboard's offline snapshot
```

Steps 5–6 take roughly 1–2 minutes total on a normal laptop.

## 6. Environment variables

| Variable | Purpose | Required? |
|---|---|---|
| `ANTHROPIC_API_KEY` | Enables the LLM-generated case narrative in `backend/app/investigation_assistant.py`. Without it, the assistant automatically falls back to a deterministic, evidence-grounded template — the dashboard works fully either way. | No |
| `PORT` | Port for the Flask API + dashboard. Defaults to `5000`. | No |

Set these in a `.env` file (see `.env.example`) or as normal environment variables before running the server. **Never commit real keys** — `.env` is gitignored.

## 7. Run & build commands

```bash
cd backend/app
python3 api.py
```

Then open **http://localhost:5000** in a browser. That's it — the same
Flask app serves both the API and the dashboard.

To re-run the pipeline after changing the data generator or model (e.g. for
the on-site final's new requirements):

```bash
cd data && python3 generate_data.py && cd ../backend/app
python3 features.py && python3 train_model.py && python3 graph_analysis.py
python3 generate_demo_snapshot.py
```

**No backend running?** Open `frontend/dashboard.html` directly in a
browser — it automatically falls back to a precomputed demo snapshot
(`frontend/demo_data.js`) with real results from the synthetic dataset, so
the dashboard is never empty even without the server.

## 10. Other configuration

- `data/generate_data.py` has all synthetic-data parameters at the top of
  the file (number of users, days simulated, how many of each scam pattern
  to inject) if you want to scale the dataset up or down.
- `backend/app/train_model.py` has a commented-out LightGBM swap if you'd

## Architecture

```
synthetic data (users, agents, transactions)
        │
        ▼
feature engineering (behavioral + network signals)
        │
        ├──► risk model (gradient-boosted trees) ──► risk score (0–1)
        │
        └──► transaction graph (networkx) ──► mule-network evidence
                        │
                        ▼
        investigation assistant (grounded narrative)
                        │
                        ▼
        analyst dashboard (Flask API + HTML/JS)
                        │
                        ▼
        human decision: approve / hold / dismiss
```

Business rules (risk thresholds, what action each level triggers) are kept
separate from the ML model's output, per the rulebook's architecture
expectations — see `risk_level()` in `backend/app/api.py`.

## Responsible AI & safety (Section 14 of the rulebook)

- **Privacy:** 100% synthetic, self-generated data. No real upay or
  customer data is used anywhere in this project.
- **Explainability:** every risk score comes with the specific feature
  values behind it (shown in the dashboard's "Signals behind this score"),
  plus feature importances for the model as a whole (`data/feature_importance.json`).
- **Fairness:** agents are deliberately excluded from mule-network scoring,
  because their legitimately high transaction turnover would otherwise look
  identical to mule behavior — see the comment in `graph_analysis.py`.
  Known limitation: the model is trained on synthetic data and has not been
  checked for behavior across real demographic groups; this would be a
  required step before any production use.
- **Security:** the scoring API validates required fields and returns
  structured errors rather than evaluating arbitrary input; the
  investigation assistant only ever receives structured, pre-computed
  evidence, never raw free text, which rules out prompt injection through
  transaction data.
- **Human oversight:** the model never blocks a transaction by itself.
  High-risk transactions are *held for review*; a human analyst makes the
  final approve/hold/dismiss call in the dashboard.
- **Transparency:** predictions (risk score), assumptions (the synthetic
  data's injected patterns), and generated text (the AI case summary) are
  kept in clearly separate fields throughout the API response — never
  merged into one opaque output.

## Known limitations & honest findings

Built and documented in the open, because the rulebook rewards "distinctive
insight," not a sales pitch:

- **Synthetic-data ceiling.** The first version of the risk model scored a
  suspiciously perfect 99.97% AUC. Investigation showed it had learned an
  overly narrow rule on one feature (wallet age at *exactly* 0.0 days vs.
  0.2 days flipped its prediction from 100% to near-zero). This was fixed
  by bucketing wallet age into robust bands and adding more realistic
  training diversity — see the comments in `features.py` and
  `train_model.py`. The lesson: a too-good metric on synthetic data is a
  signal to dig in, not celebrate.
- **Graph detection precision.** The mule-network detector catches 6/6
  injected mule rings (100% recall) with 6 false positives out of 2,006
  candidate wallets checked — a small number of legitimate users with
  naturally bursty receiving patterns get flagged too. This is disclosed
  rather than hidden, and is exactly why the system holds transactions for
  human review instead of blocking automatically.
- **Behavioral detection has a real blind spot.** For a user whose job
  involves constantly transacting with strangers (a street vendor, an
  agent), sender-side behavioral signals are weak by design, since
  "new recipient" is their normal pattern. The system leans on
  recipient-side and graph evidence for these users instead — see the
  reasoning that shaped this design further down in the project's chat history.

## Path to validation & scale (Section 2, 11, 13 of the rulebook)

1. **Controlled validation:** re-run the same pipeline against anonymized,
   governed upay transaction samples (with appropriate approvals) to check
   whether the synthetic patterns generalize to real behavior.
2. **A/B the threshold:** tune the 0.4 / 0.7 risk cutoffs against real
   false-positive tolerance and investigation team capacity.
3. **Expand the mule graph:** real data would allow multi-hop tracing
   (money passing through 2–3 wallets before cash-out), not just
   single-hop fan-in detection.
4. **Swap in LightGBM/XGBoost** for the production model once there's an
   unrestricted environment to install them (the architecture doesn't
   change — see the comment in `train_model.py`).
5. **Add a real decision store** (database instead of in-memory) and an
   audit log of every analyst decision for compliance.
